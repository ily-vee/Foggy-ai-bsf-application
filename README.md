# Foggy AI — Black Soldier Fly Farming Assistant

An AI assistant for Black Soldier Fly (BSF) farmers — identifies life stages from photos, answers farming questions grounded in real reference material, does deterministic math instead of hallucinated arithmetic, and supports text, image, and voice note input.

## What This Is

Foggy AI combines four components into one assistant:

1. **SigLIP2** (LoRA fine-tuned) — classifies a farmer's photo into one of 5 BSF life stages (egg, larva, prepupa, pupa, adult), with out-of-distribution detection to catch photos that aren't BSF at all.
2. **Qwen2.5-VL-3B-Instruct** (QLoRA fine-tuned, GGUF-quantized) — generates the actual advice, with real visual reasoning on follow-up questions about a photo (not just a text description of it).
3. **Hybrid retrieval** (dense embeddings + BM25) — grounds every answer in real source documents instead of the model's own memorized (and sometimes wrong) knowledge.
4. **Deterministic calculators** — feed quantity, stage-timing, and moisture-dilution math computed in real Python code, not generated by the LLM.

Plus: voice note transcription (Whisper), a domain-scope gate that declines off-topic questions, and bounded conversation history for multi-turn context.

## Architecture

```
Farmer (WhatsApp, via Temboa's app backend)
        |
        v
Orchestration Service (this repo, containerized, runs on the node)
   +- SigLIP2 classification + OOD check       (local, in-process)
   +- Hybrid retrieval (RAG)                    (local, in-process)
   +- Deterministic calculators                 (local, in-process)
   +- Domain-scope gate                         (local, in-process)
   +- Whisper transcription (voice notes)       (local, in-process)
   +- Generation -------------------------> llama-server (HTTP)
                                                  |
                                                  v
                                     Qwen2.5-VL-3B GGUF model
                               (owned/deployed by Temboa's node agent,
                                via their model manifest/registry system)
```

**Key architectural decision:** the orchestration layer (steps above) and the raw model server are two separate, independently-deployed things. The model file flows through Temboa's own manifest/registry/node-agent mechanism; this repo's container calls the resulting `llama-server` instance over a plain HTTP API. Neither side needs to know the internals of the other — see [Integration Contract](#integration-contract).

## Project History

This project went through several real architectural pivots, each driven by a concrete problem discovered in testing — worth understanding for anyone picking this up later, since some of the current design choices only make sense in light of what came before.

**Phase 1 — Text-only hybrid.** Started with SigLIP2 for classification and a text-only Qwen2.5-3B-Instruct for generation, fed a text description of the classifier's output. Early testing surfaced fabricated citations (fake DOIs), CJK/non-Latin token leakage, and free-generated arithmetic that produced fabricated-looking numbers. Fixed via prompt/training changes, a hard token-suppression list, and replacing LLM-generated math with deterministic calculators.

**Phase 2 — Real RAG.** Replaced a 5-line static knowledge dict with genuine hybrid dense+BM25 retrieval over real source documents, with a relevance floor to avoid forcing irrelevant context into ungrounded queries.

**Phase 3 — Voice notes.** Added Whisper-based transcription so farmers can ask by voice. Domain-vocabulary biasing added to reduce mistranscription of BSF-specific terms.

**Phase 4 — Vision-language upgrade.** The original architecture could only *describe* an image via heuristic color/blur/sharpness analysis — it couldn't actually *see* it. Migrated to Qwen2.5-VL for genuine visual reasoning on follow-up questions ("do they look healthy?"), fine-tuned via QLoRA on a small, deliberately human-verified pilot dataset (visual observations were written by a human who actually looked at each photo — never auto-generated, to avoid training the model to produce fluent-but-ungrounded visual descriptions).

**Phase 5 — GGUF/CPU conversion.** Converted the fine-tuned VLM to GGUF format for CPU inference via `llama.cpp`, per the target deployment architecture (Temboa's node-based model hosting). Validated that a documented failure mode (fine-tuned VLM to GGUF conversion producing garbage output) did not affect this specific model.

**Phase 6 — Retargeted orchestration.** Retargeted the Python engine to call the GGUF model via `llama-server`'s HTTP API instead of loading model weights in-process — enabling the current split where the orchestration layer and the model server deploy independently.

**Phase 7 — Containerization.** Packaged the orchestration layer as a Docker container for node deployment, decoupled from the model file itself.

## Setup

### Running the orchestration service locally

1. Build: `docker build -t foggy-orchestration .`
2. Have `llama-server` running separately (see [Integration Contract](#integration-contract) for how the two connect)
3. Run: `docker run -p 9000:9000 -e FOGGY_LLAMA_SERVER_URL=<llama-server address> foggy-orchestration`
4. Test: `python test_service_integration.py http://localhost:9000 <path-to-test-image>`

### Rebuilding the retrieval index

```bash
python core/ingest.py   # reads knowledge_docs/, writes foggy_vector_db/
```

## Integration Contract

The orchestration service exposes:

**`GET /health`** returns `{"status": "ok", "engine_loaded": true}`

**`POST /chat`**

Request:
```json
{
  "text": "What do BSF larvae eat?",
  "image_base64": null,
  "audio_base64": null,
  "history": [
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ]
}
```
All fields except at least one of `text`/`image_base64`/`audio_base64` are optional. `history` should be whatever was returned from the *previous* call for this same user/conversation — omit it (or pass `[]`) to start fresh.

Response:
```json
{
  "response": "BSFL are insatiable voracious feeders...",
  "history": [ ]
}
```
(`history` in the response is the updated turn list — persist this and pass it back next call.)

**Media handling:** images/audio are received as base64, written to a temp file for processing, and deleted immediately after — nothing is retained by this service.

**Environment variables:**

| Variable | Purpose | Default |
|---|---|---|
| `FOGGY_LLAMA_SERVER_URL` | Address of the running `llama-server` instance | `http://127.0.0.1:8080/v1/chat/completions` |
| `FOGGY_WHISPER_MODEL` | Whisper model size | `medium` |
| `FOGGY_WHISPER_DEVICE` | `cpu` or `cuda` | `cpu` (set in Dockerfile) |
| `PORT` | Service listen port | `9000` |

## Known Limitations

- **Latency:** CPU inference of a 3B VLM is slow - expect tens of seconds per response, more for image queries. This is a hardware/architecture constraint, not a bug.
- **Small pilot fine-tuning dataset:** the current VLM adapter was trained on a deliberately small, human-verified set of examples. Expect solid performance on the 5 known life stages, less reliability on unusual edge cases.
- **Domain-scope gate is a heuristic, not exhaustive** - catches clearly off-topic queries but isn't guaranteed on every phrasing; the model's own trained behavior fills some gaps but isn't a substitute for the gate firing correctly.
- **No GPU utilization by default** - this container runs CPU-only; if a node has a GPU, `llama-server` (managed separately by the node agent) can use it via `-ngl`, but this orchestration container's own SigLIP2/retrieval/Whisper components run CPU-only regardless.

## Retraining / Expanding the Model

1. Add rows to a manifest (image path, stage, a **human-written** description of what's actually visible in that photo, a farmer-style question) - see `training/build_foggy_vlm_dataset.py`'s docstring for the exact schema.
2. `python training/build_foggy_vlm_dataset.py manifest.csv new_dataset.jsonl`
3. `python training/train_qwenvlm_qlora.py new_dataset.jsonl models/qwen_vlm_bsf_qlora`
4. `python training/merge_lora_for_gguf.py models/qwen_vlm_bsf_qlora models/qwen_vlm_bsf_merged`
5. Convert to GGUF via `llama.cpp`'s `convert_hf_to_gguf.py` (language weights + `--mmproj` for the vision tower), then quantize with `llama-quantize`.

## Testing

`test_service_integration.py` exercises the containerized service end-to-end: health check, plain text query, multi-turn history, domain-scope gate, reset command, and image query. Run it against a live container before any deployment.
